# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Panel de Compras y Bienestar" (Sinco) — a purchasing and employee-wellbeing app with two modules, Compras and Bienestar (Bienestar and Fundación activities). Internal ids such as the `panel-compras` MCP server name keep the old name on purpose: changing them would break existing connections. Migrated from a single-file HTML app (vendored jsPDF/jspdf-autotable/html2canvas, inline JSON data) into **Next.js (App Router, JavaScript, not TypeScript)** + **React** + **Prisma ORM on PostgreSQL**. The original's "regenerate and republish the whole HTML file" persistence model was replaced with a real REST API + database.

The repo is split into two independent Next.js apps, sibling folders at the repo root:

- **`backend/`** — API-only Next.js app: `app/api/*` routes, Prisma/PostgreSQL, auth. Runs on port **3001**.
- **`frontend/`** — the UI: all page routes (dashboard, registros, usuarios, auditoría, agente IA, login). Runs on port **3000**. Never touches Prisma directly — every data read/write goes through HTTP calls to the backend.

The seed data in `backend/prisma/seed-data.json` is **example data only**, not the real business dataset (~479 records in the original). See "Loading real data" below.

## Conventions

- **Every feature that creates, edits, deletes, or otherwise manages state must be audited.** Any new mutating endpoint/lib (not just `records`/`maestros`/`users`/`proveedores`/`presupuestos`/`permissions`/`reports`, which already do this) needs a corresponding `logXCreate`/`logXUpdate`/`logXDelete` (or equivalent) call in `backend/lib/audit.js`, a field-label map in `backend/lib/auditLabels.js` (+ its `frontend/lib/auditLabels.js` copy) for the diff, and an `entityType` entry in `ENTITY_LABELS` — following the exact pattern already used for `record`/`maestro`/`proveedor`/`user`/`presupuesto`/`permiso`/`informe`/`calificacion`. Audit calls are fire-and-forget (`.catch(() => {})`) so a logging failure never blocks the actual write. Do this as part of building the feature, not as an afterthought.

- **Every table (DB model) records when and by whom a row was created.** New models need `createdAt DateTime @default(now())` plus the creator as `creadoPorUserId String?` and a name snapshot `creadoPorNombre String?` (no FK, same as the other references to `User`; use "Importación Excel" / "Migración histórica" when no person created it). Set both on create from the session user, show them where the row is detailed, and keep them in the audit entry. When adding a column to an existing table, backfill old rows in the same migration. Existing tables that predate this rule and lack the creator columns: bring them in line when you next touch them.
- **Text is always UTF-8; a damaged character (U+FFFD, the replacement-character diamond that replaces an accent or the ñ when the encoding is wrong, e.g. a name saved as Persona P-diamond-rez) can never be saved.** The database enforces it for every table with the trigger `trg_texto_sin_danos` (migration `texto_sin_caracteres_danados`): a write that adds a U+FFFD to a row is rejected (`check_violation`), whether it comes from the app, a script or an import. `backend/middleware.js` also rejects JSON bodies carrying it with a clear 400, and `apiError` turns a trigger rejection into a 400 (never a raw 500). **Every new table must be protected in its own migration with `SELECT proteger_texto_tabla('<table>');`** — `npm run db:verificar-texto` (backend/) lists unprotected tables and any damaged data (exit code 1), run it before deploying. Never type accents through a Windows console/`curl`/PowerShell without UTF-8 (that is how bad bytes were born): test non-ASCII text with Node `fetch` or the UI, and make import scripts read files as UTF-8 (`iconv-lite` for legacy Latin-1/CP1252 files) instead of letting them guess. Never put a literal U+FFFD in source files.

- **Money uses ISO 4217.** New code stores the currency code next to every amount (`moneda`, validated with `Intl.supportedValuesOf("currency")`, default `COP`), never adds different currencies together, and shows amounts with the code: "COP 1.234.567" (`frontend/lib/moneda.js#fmtMoneda`, `backend/lib/tesoreria/comun.js#fmtMoneda`). Tesorería follows it everywhere; Compras and Bienestar still show "$" with `fmtCOP` (change them only when asked).

- **Every money field is typed with thousands separators (dots, es-CO: 1.234.567), never as a plain number.** Use `frontend/components/MoneyInput.jsx` for any input of a value, price, cost, budget, balance, salary or amount filter — never `<input type="number">` for money. It keeps the plain number in state ("1234567", or "1250.5" with `decimales`) and shows it formatted while typing; `prefix` is the ISO 4217 code in new code (`"COP"`, the account's currency in Tesorería) or `"$"` in the older Compras/Bienestar forms, `null` inside table cells; `decimales` for currencies with cents (typed with a comma); `permitirNegativo` for balances. Non-money numbers (years, percentages, counts) stay as normal numeric inputs.

- **Every table must be paginated.** Any new or modified table that lists rows (records, proveedores, usuarios, auditoría, informes, etc.) needs client- or server-side pagination, in the same format as the Registros table (`RegistrosView.jsx`): a `table-footer` with a `Tamaño` selector (`PAGE_SIZES`, default 25 / 50 / 100; a table inside a modal, and the purchase lists of the activity form, start at 10: 10 / 25 / 50 / 100), `page-btns` with Anterior / Siguiente, a `count-note` with "Página X de Y" and a total count. Reset to page 1 whenever a filter, search or tab changes, and clamp the current page when the result set shrinks. Long text cells (names, descriptions) must truncate with the `desc-tooltip-wrap` / `desc-text` / `desc-tooltip-bubble` hover pattern instead of wrapping, and rows stay single-line and compact. Short summary lists capped at a few rows (e.g. top-5) may skip pagination only if they link to the full paginated table.

## Architecture

### Cross-app communication (frontend ↔ backend)

- Browser-side `fetch("/api/...")` calls (client components, `frontend/lib/api.js`) stay as relative paths — `frontend/next.config.js` has a `rewrites()` block that proxies `/api/:path*` to `BACKEND_URL` (env var, defaults to `http://localhost:3001`), so from the browser's perspective everything is same-origin (no CORS, cookie just works).
- Server Component data loads (`frontend/app/**/page.js`) call the backend directly via `frontend/lib/backendFetch.js`, which forwards the incoming request's session cookie manually (a server-to-server `fetch` does not do this on its own, rewrites don't apply to it either).
- `frontend/lib/auth.js#getSessionUser()` replaces the old direct-Prisma version — it calls `GET /api/auth/me` on the backend instead.
- Both apps need the **same** `SESSION_SECRET` in their `.env` (each signs/verifies the session cookie independently with its own copy of `lib/session.js`).

### Backend (`backend/`)

- **Data layer**: `prisma/schema.prisma` defines `Record` (a single purchase record: dates, area, responsable, estado, categoría, proveedor, valores `valorConIva`/`valorSinIva`/`valorCot`, `radicado` boolean, etc., mapped to table `records`), `Meta` (singleton row `id=1` tracking `sourceFile`/`sourceSheet`/`nextLocalSeq`, mapped to `meta`), and `User` (`nombre`, `email` unique, `password` — a bcrypt hash, `role`, `activo`, mapped to table `users`), plus `AuditLog`, agent-chat `Conversation`/`Message`, `Maestro`, `PresupuestoAnio`/`Presupuesto`/`PresupuestoCategoria`, `RolePermission`, and `ReportConfig` (see below for each). Schema changes go through `prisma migrate dev`, never hand-edited SQL. **New tables going forward use an auto-incrementing integer `id` (`Int @id @default(autoincrement())`), not a cuid** — existing models keep their cuid `id` as-is, this only applies to models created from now on.
- **`lib/prisma.js`**: singleton `PrismaClient` via `globalThis`, required to avoid exhausting connections under Next.js dev hot-reload.
- **`lib/records.js`**: all record data-access + validation (`listRecords`, `getMeta`, `createRecord`, `updateRecord`, `patchRecord`, `deleteRecord`, `sanitizeInput`, `toClientRecord`). `lib/users.js` is the equivalent for `User` (`listUsers`, `createUser`, `updateUser`, `deleteUser` — hashes passwords with `bcryptjs` before writing, never stores plaintext). Route handlers are thin wrappers around these modules — validation errors are thrown as `Error` with a `.status` property (e.g. 400) that route handlers read directly. `lib/apiGuard.js#requirePermission(feature)` centralizes the "get session user + check permission, else 403" boilerplate shared by nearly every route handler (returns `{ user, denied }` — return `denied` if non-null); `apiError(err)` centralizes the `{ error: err.message }, { status: err.status || 500 }` catch-block response.
- **Auth**: `lib/session.js` signs/verifies a small HMAC (Web Crypto, not Node `crypto`) session token so it works in both the Node route-handler runtime and the Edge `middleware.js` runtime; the token is stored in an httpOnly `session` cookie. `lib/auth-server.js#getSessionUser()` reads that cookie and re-fetches the user from the DB, exposed to the frontend via `GET /api/auth/me` (which also returns the caller's effective `permissions` map, see Matriz de permisos below). `middleware.js` gates every `/api/*` route except `/api/auth/login`: unauthenticated requests get a 401, non-admins get a 403 on `/api/users`, `/api/agent`, `/api/audit`. `lib/roles.js` defines the four roles and the `canX(role)` permission helpers — the **static default** for what each role can do; both the frontend UI (a duplicated copy of this file, hides buttons) and route handlers read it as a fallback, so a permission change still belongs in both copies (`backend/lib/roles.js` and `frontend/lib/roles.js` must stay in sync). The actual **runtime source of truth is the Matriz de permisos** (`lib/permissions.js`, see below), which can override these defaults per role.
  - **Roles**: `admin` (full access, cannot be restricted via the permissions matrix), `registro` (dashboard + full record CRUD by default, no user admin), `legalizar` (records table only, can edit but not create/delete by default), `radicar` (records table only, can only toggle the "radicado" check by default) — but any non-admin role's access to a given feature can be overridden at runtime by an admin via the Matriz de permisos.
  - Default seeded admins (see `prisma/seed.mjs`): `admin@example.com` / `admin2@example.com`, password `12345678` (bcrypt-hashed before insert) — change/rotate before any real deployment.
- **Roles personalizados (`lib/rolesCatalogo.js`, `lib/rolesPersonalizados.js`, `app/api/roles/*`, `frontend/components/RolesView.jsx`, tab Usuarios › Roles)**: besides the 5 system roles in `lib/roles.js` (they keep hard-coded rules: Legalizar's editable fields, radicado…), admins create roles in the UI (model `RolPersonalizado`, table `roles`; `User.role` stores its `clave`, a lower-case slug). A custom role has **no** default permissions: its features are `RolePermission` rows, i.e. the same Matriz (which now shows one column per role, system + custom). Editing a role's features goes through `setPermission` (audited as `permiso`); create/rename/delete are audited as `rol`. System roles can't be renamed or deleted; a custom role can't be deleted while users have it; Administrador can't be modified. Anything that validates or labels a role must use `rolesCatalogo.js` (`esRolValido`, `nombreDeRol`, `todosLosRoles`), never `ROLE_LIST` alone; `/api/auth/me` returns `roleLabel` for display. Seeded role **Bienestar** (migration `roles_personalizados`): viewBienestar, editBienestar, viewRegistros, viewAgenteIA, viewNotificaciones. Seeing Registros is now the Matriz feature `viewRegistros` (default: the Compras roles), so a custom role can be given it; roles without it are sent to /bienestar or /proveedores, and the landing page falls back to /bienestar.
- **Matriz de permisos (`lib/permissions.js`)**: a runtime permissions layer on top of `lib/roles.js`'s static defaults, gated by the dynamic feature `viewUsuarios` (not a hardcoded `role === "admin"` check) and surfaced in the frontend inside `UsuariosView.jsx` (`components/PermissionsMatrix.jsx`). `FEATURES` is a hardcoded catalog of toggleable features, each with a `modulo` (Compras, Bienestar or General, the tabs of the Matriz; a new feature must have one) and a `defaultRoles` list. Bienestar and Fundación have separate features (`viewDashboardBienestar`/`viewBienestar`/`editBienestar`, `viewDashboardFundacion`/`viewFundacion`/`editFundacion`, plus the shared `viewMaestrosBienestar`): routes of one activity use `apiGuard.js#requirePermisoActividad(id, "ver"|"editar")`, which picks the feature from the activity's línea. Each default list matching `lib/roles.js`'s current behavior. `isRoleAllowed(role, featureKey)` — called from almost every route handler instead of a static role check — looks up an exception row in `RolePermission`; if none exists (or the lookup fails), it falls back to `defaultRoles`, so a data/connection issue never silently revokes access. `admin` always returns `true`, regardless of any stored row. `setPermission()` upserts an override and audit-logs the change (`entityType: "permiso"`). `GET /POST /api/permissions` exposes `getFullMatrix()`/`setPermission()`; `getEffectivePermissions(role)` backs the `permissions` map returned by `GET /api/auth/me`.
- **Maestros (`lib/maestros.js`, `app/api/maestros/*`)**: admin-configurable catalogs (`Maestro` model) backing the `<select>` options in the records form — one `tipo` per `Record` field (`area`, `responsable`, `estado`, `categoria`, `medioPago`, `estadoLegalizacion`), replacing what used to be hardcoded lists, plus the Proveedores catalogs (`areaProveedor` — its own area list, separate from Compras `area` —, `tipoProveedor` (criticidad), `clasificacionMonto`, `tipoServicio`, `motivoExcepcion`). `MODULO_POR_TIPO` groups them by module: Compras catalogs are managed by Compras roles, Proveedores catalogs by whoever has `editProveedores`. A value **in use** in either module (measured by id reference, see `USOS_POR_TIPO`) cannot be renamed or deleted, only deactivated. The Ciclo de proveedores config (fecha de corte) lives inside the Maestros page (`/maestros?seccion=cicloProveedores`); `/ciclo-proveedores` only redirects there. `TIPOS_MAESTRO` is duplicated in `frontend/lib/maestrosTipos.js` (no Prisma dependency) — keep both in sync, same pattern as `lib/roles.js`. Listing (`GET`) only requires being authenticated (every role needs it to populate the records form); writing requires `viewMaestros` (default: admin and proveedores).
  - **Referential integrity convention**: every `Record` field backed by a catalog is referenced by **id**, never by text — `Record.<campo>Id` (`areaId`, `estadoId`, `categoriaId`, `medioPagoId`, `estadoLegalizacionId` → `Maestro.id`; `responsableUserId` → `User.id`; `proveedorNit` → `Proveedor.nit`, a real FK with ON UPDATE CASCADE / ON DELETE RESTRICT). The plain-text column (`area`, `estado`, `proveedor`, etc.) is kept only as a snapshot for export/history; `lib/records.js#hydrateConDatosActuales()` resolves the live value from the catalog by id on every read (`listRecords`/create/update) and overrides the snapshot with it — so renaming a value in Maestros/Usuarios/Proveedores is instantly reflected on every existing record without touching them. Writes always validate the id against the catalog (`requireMaestroCampo`/`requireProveedorDelCatalogo`/`requireResponsableDelCatalogo`) and recompute the snapshot text server-side — the client's text is never trusted. Audit "before" snapshots intentionally skip hydration, so the log preserves the value as it was at that point in time. **Apply this same pattern to any new catalog-backed field.**
- **Proveedores (`lib/proveedores.js`, `lib/proveedoresCiclo.js`, `lib/proveedoresCicloReglas.js`, `app/api/proveedores/*`)**: `Proveedor`'s primary key is the **NIT** (`nit`, normalized by `proveedoresCicloReglas.js#normalizeNit`: Colombian NIT without verification digit, foreign tax ids alphanumeric uppercase, `PENDIENTE-…` for providers not yet formally registered). Every relation points to the NIT (`Record.proveedorNit`, `ProveedorCiclo/ProveedorProceso/ProveedorChecklist.proveedorNit`) with ON UPDATE CASCADE, so correcting a NIT (`updateProveedor` → `cambiarNit`) propagates by itself; non-FK snapshots (`Record.nit`, `CalificacionProveedor.proveedorNit`) are updated in the same transaction. Routes are `/api/proveedores/[nit]`; the client object keeps `id` as an alias of `nit`. Duplicate NITs are rejected server-side and checked live from the form via `GET /api/proveedores/verificar-nit`. The yearly update cycle is computed from `fechaActualizacion` (last update), never from `createdAt`; approving a provider (cycle state → `actualizado`, single, bulk or from the edit form) requires the user to enter that date (`fechaActualizacion` aaaa-mm-dd, inside the current cycle and not in the future, `proveedoresCiclo.js#fechaActualizacionDe`), which becomes both `fechaActualizacion` and `aprobadoAt` and is audited; `esExcepcion` providers (settable on create/edit, needs a `motivoExcepcion`) never take part in the cycle. Excel migration/normalization/integrity scripts live in `backend/scripts/proveedores/` (see its README; config in `mapeoProveedores.json`).
- **Valoración IA de compras (`lib/valoracionIA.js`, `lib/valoraciones.js`, `lib/valoracionAuto.js`, `app/api/records/[id]/valoracion`, `app/api/proveedores/[nit]/compras`)**: cada compra radicada recibe una `ValoracionCompra` (una por registro, puntajes 1–5 de la compra y del proveedor + observaciones que explican por qué + factores). `valoracionIA.js` es el núcleo puro (solo imports relativos, recibe el cliente Prisma) que arma el contexto completo del registro, del proveedor y de sus compras ANTERIORES, aplica la rúbrica y guarda; lo usan la app y `scripts/valoraciones/valorarRegistrosRadicados.mjs`. Al radicar, el frontend abre `ValoracionModal` que genera y guarda la valoración (`POST`); se ve en la columna Valoración IA de Registros y, en el detalle del proveedor, en la pestaña Compras y calificaciones (historial + calificación general = promedio del puntaje de proveedor), que también alimenta la columna Calificación IA de la tabla de proveedores. `valoracionAuto.js` (arrancado desde `instrumentation.js`) valora en segundo plano, al arrancar el backend y cada 30 min, las radicadas sin valoración, así al publicar los registros existentes quedan valorados solos (idempotente; usa `ANTHROPIC_API_KEY` del servidor; `VALORACION_AUTO=0` lo desactiva). Reglas de la rúbrica a respetar: la fecha de registro solo se usa si no es de una carga histórica (>30 registros creados el mismo día) y las valoraciones previas de la IA nunca se realimentan como contexto.
- **Presupuesto (`lib/presupuestos.js`, `app/api/presupuestos/*`)**: per-year, per-area purchasing budgets (`PresupuestoAnio`, `Presupuesto`, `PresupuestoCategoria` models). A year's `modo` is either `"area"` (one total per area) or `"categoria"` (split across categories, summed for the area total); switching modes when budgets already exist requires `confirm: true` and deletes the existing ones (`POST /api/presupuestos/modo`). Everything (including reads) is gated by `viewPresupuesto` (default: admin only). Feeds the budget-risk alert below.
- **Bienestar: actividades y cronograma (`lib/actividadesBienestar.js`, `app/api/actividades/*`, `frontend/components/bienestar/*`, page `/bienestar`)**: `ActividadBienestar` (table `actividades_bienestar`, Int id) is one activity of the yearly plan: nombre, fecha (YYYY-MM-DD string like Record dates), línea (Bienestar/Fundación), estado — lifecycle **creada → programada → ejecutada → cerrada** (only creada may lack a date; cerrada receives no new purchases) —, presupuesto asignado, inscritos/asistentes, responsable and creator. A purchase is associated from the Registros form (create or edit): `Record.actividadId` (real FK, ON DELETE RESTRICT — an activity with purchases cannot be deleted) + `Record.actividad` name snapshot, resolved to the current name by `hydrateConDatosActuales` (same catalog pattern as proveedor); the activity's spend is the sum of `valorConIva` of its purchases. The dashboards' main cards have the same "Explicar" button as Compras (`components/KpiExplain.jsx`, `POST /api/actividades/explicar`: figures come from the server, never the client). Each view is its own page in the Bienestar menu (`/bienestar`, `/bienestar/actividades`, `/bienestar/cronograma`, all through `components/bienestar/BienestarPagina.jsx`): **Resumen** (dashboard from `GET /api/actividades/resumen`: KPIs tagged by source Bienestar/Compras/Cruce, monthly spend of associated purchases vs. attendees, deterministic "Lectura del año", cost per attendee, spend by category, upcoming activities), **Actividades** (paginated table, filters) and **Cronograma** (yearly 12-month view and monthly calendar with Colombian holidays, `+` per day to create). Creating and editing an activity is a page, not a modal (`/bienestar[/fundacion]/actividades/nueva` and `/[id]/editar`, `components/bienestar/ActividadFormulario.jsx`), with one tab per topic (La actividad · Presupuesto y costo — ejecutado = legalized purchases, en trámite = the rest · Asistencia · Compras). `fecha` is the start date; `fechaFin` is optional for multi-day activities (never before `fecha`; equal to it is stored as null) and the cronograma shows them on every day and month they touch. State colors are a fixed traffic-light (`--est-*` tokens, independent of the module theme). Purchases can also be associated **from the activity** (`POST/DELETE /api/actividades/[id]/compras`, `GET /api/actividades/compras-disponibles`; needs only editBienestar, touches only `actividadId`, audited on the purchase via `records.js#asignarActividadACompra`), and "Solicitar compra" sends Compras a request (see Solicitudes de compra). Reading the list only needs authentication (the purchase form needs it); `viewBienestar` gates the page and the detail, `editBienestar` create/edit/delete (default admin + registro). Audited as `entityType: "actividad"`. `scripts/bienestar/importarActividades.mjs <archivo.json> [--confirmar]` loads the plan from the Bienestar Excel base export (idempotent by nombre+fecha).
- **Bienestar: participantes, inventario, formulario público y cierre (`lib/participantesBienestar.js`, `lib/inventarioBienestar.js`, `lib/bienestarExcel.js`, `app/api/actividades/[id]/{participantes,inventario,formulario}`, `app/api/publico/inscripcion/[token]`, `frontend/components/bienestar/FichaActividad.jsx`, `InscripcionPublica.jsx`)**: the module answers: spend vs. budget, who registered and did not attend (and why), participation %, participation by area, inventory used vs. left over, and a rating when closing. **Bienestar and Fundación are kept apart** (each with its own Resumen/Actividades/Cronograma under `/bienestar` and `/bienestar/fundacion`; `?linea=` on the API; Spend in the module, for both líneas and for Nova, only ever counts purchases ASSOCIATED to an activity of that línea, in the month of the activity; unassociated purchases show no value there). `ParticipanteActividad` (one row per person and activity: inscrito, asistio true/false/null, motivoInasistencia from `MOTIVOS_INASISTENCIA`, calificación 1-5, observación, `datos` JSON with the activity-specific fields — sensitive ones (health, EPS, blood type, emergency contacts, minors…) are only returned to editBienestar —, origen formulario/importacion/manual, autorizaDatos) drives the activity counts (`sincronizarConteos`: attendees are only recalculated once some attendance is recorded). `InventarioActividad` (cantidad, usado, costoUnitario → sobrante and its cost). Closing is not a selectable state but an action ("Cerrar actividad", ficha and edit form, confirmation modal `CerrarActividadModal`): only from ejecutada, requires a 1-5 `calificacion` (+ comentarioCierre, cerradaPor/At) and closes the public form. A closed activity can no longer be modified (the backend rejects edits to it, its participants, inventory, photos, form and associated purchases; a purchase's own Compras data still changes). Public form: per-activity random `formularioToken`, `formularioCampos` from `PLANTILLAS_FORMULARIO` (general/carrera/torneo/familiar/fundación); `/inscripcion/<token>` (frontend, no session) → `/api/publico/inscripcion/<token>` (no session, rate-limited by IP, both middlewares let it through), requires the Ley 1581 data authorization and rejects a duplicate document. Excel import (`bienestarExcel.js`, also used by scripts): columns recognised by header (Forms exports, attendance lists; X/SI/OK = attended, "No asiste…" = not + reason), people matched by document, exact name or `buscarPorNombre` (≥2 shared words, unique candidate). The activity page (`/bienestar[/fundacion]/actividades/[id]`) has Resumen / Participantes (paginated, attendance per person, the three Excel imports, per-person data) / Inventario / Compras / Formulario tabs. The Resumen has the same Mensual/Anual + Año (+ Mes) control as the Compras dashboard (`?mes=`). Migration of the Excel folder: `scripts/bienestar/importarParticipantes.mjs <carpeta> [--confirmar]` (file → activity map inside, then the Fundación base "X" marks); `reconstruirLocal.mjs` cleans and rebuilds it all in the local DB and `generarMigracionCarga.mjs` writes the data migration (loads only if `actividades_bienestar` is empty, never writes the sensitive Excel fields). Audited as `participante` / `inventario` / `formularioActividad` with the activity id as recordId.
- **Bienestar: importar con Nova, análisis, fotos y Fundación**: (1) `lib/importacionNova.js` + `POST /api/actividades/[id]/participantes/importar-nova` (`ImportarNovaModal.jsx`): three imports in the Participantes tab (programados, asistentes, calificaciones). ### Files duplicated across both apps

`lib/session.js`, `lib/roles.js`, and `lib/auditLabels.js` have no Prisma/Node-only dependency, so each app keeps its own copy (`backend/lib/*` and `frontend/lib/*`) rather than sharing a package. `TIPOS_MAESTRO` is duplicated the same way (`backend/lib/maestros.js` ↔ `frontend/lib/maestrosTipos.js`). **When editing any of these, update both copies.**

Anthropic (Claude) is the only AI provider configured in the app — there is no Gemini fallback. `backend/lib/anthropic.js` wraps the Messages API (`ANTHROPIC_API_KEY` env var), `backend/lib/anthropicModels.js` is the model catalog and the model ORDER (`modelosEnOrden()`): every environment uses Claude Haiku 4.5 (an attempt on 2026-11-05 to use Opus/Sonnet in production made Nova answer "Error al conectar con el servicio de IA (401)" and was reverted). `ANTHROPIC_MODELOS` / `ANTHROPIC_MODELOS_AUTO` (comma-separated ids; automatic = work started inside `enSegundoPlano`) change the order without touching code — check first that the production key allows those models. `conModelos(llamada)` runs a call through that list with fallback (used by `aiChatCascade.js` and `aiStructured.js`; a 401/403 does not jump). `DEFAULT_ANTHROPIC_MODEL` = the first of the list, `backend/lib/aiChatCascade.js` is the streaming entry point used by the Agente IA chat, and `backend/lib/aiStructured.js` is the non-streaming structured-JSON entry point used by Informes automáticos, moderation, "Explícame este número", etc. All roles use the same models — there is no paid/free distinction or per-role AI model gating. Cost controls: the Nova chat sends only the INDEX of the procurement policy and the app guide — Nova fetches the sections it needs with the `consultar_referencia` tool (`lib/referenciasNova.js`); the static prefix is cached for 1 h and the last message is a cache breakpoint (incremental caching across tool rounds); tool results are capped at 15k chars and the history at 12 messages; `generateStructuredJson` caches identical requests for 2 h (`cache: false` opts out, used by the purchase valuations). `AI_USAGE_LOG=1` prints each call's `usage` to the backend log to measure real consumption.

## Loading real data

The seed (`backend/prisma/seed-data.json`, loaded by `backend/prisma/seed.mjs` via `npm run db:seed`) is illustrative sample data only. To load the real dataset, replace `backend/prisma/seed-data.json` with a real export in the same shape (`{"records": [...], "meta": {...}}`) and re-run `npm run db:seed` from `backend/` (this does a full `deleteMany()` + recreate, then upserts `Meta`).
