# Módulo Compras: catálogos, proveedores, valoración IA, presupuesto y agentes

Detalle movido desde `CLAUDE.md` (sin cambios de contenido). Las convenciones generales siguen en `CLAUDE.md`.

- **Maestros (`lib/maestros.js`, `app/api/maestros/*`)**: admin-configurable catalogs (`Maestro` model) backing the `<select>` options in the records form — one `tipo` per `Record` field (`area`, `responsable`, `estado`, `categoria`, `medioPago`, `estadoLegalizacion`), replacing what used to be hardcoded lists, plus the Proveedores catalogs (`areaProveedor` — its own area list, separate from Compras `area` —, `tipoProveedor` (criticidad), `clasificacionMonto`, `tipoServicio`, `motivoExcepcion`). `MODULO_POR_TIPO` groups them by module: Compras catalogs are managed by Compras roles, Proveedores catalogs by whoever has `editProveedores`. A value **in use** in either module (measured by id reference, see `USOS_POR_TIPO`) cannot be renamed or deleted, only deactivated. The Ciclo de proveedores config (fecha de corte) lives inside the Maestros page (`/maestros?seccion=cicloProveedores`); `/ciclo-proveedores` only redirects there. `TIPOS_MAESTRO` is duplicated in `frontend/lib/maestrosTipos.js` (no Prisma dependency) — keep both in sync, same pattern as `lib/roles.js`. Listing (`GET`) only requires being authenticated (every role needs it to populate the records form); writing requires `viewMaestros` (default: admin and proveedores).
- **Proveedores (`lib/proveedores.js`, `lib/proveedoresCiclo.js`, `lib/proveedoresCicloReglas.js`, `app/api/proveedores/*`)**: `Proveedor`'s primary key is the **NIT** (`nit`, normalized by `proveedoresCicloReglas.js#normalizeNit`: Colombian NIT without verification digit, foreign tax ids alphanumeric uppercase, `PENDIENTE-…` for providers not yet formally registered). Every relation points to the NIT (`Record.proveedorNit`, `ProveedorCiclo/ProveedorProceso/ProveedorChecklist.proveedorNit`) with ON UPDATE CASCADE, so correcting a NIT (`updateProveedor` → `cambiarNit`) propagates by itself; non-FK snapshots (`Record.nit`, `CalificacionProveedor.proveedorNit`) are updated in the same transaction. Routes are `/api/proveedores/[nit]`; the client object keeps `id` as an alias of `nit`. Duplicate NITs are rejected server-side and checked live from the form via `GET /api/proveedores/verificar-nit`. The yearly update cycle is computed from `fechaActualizacion` (last update), never from `createdAt`; approving a provider (cycle state → `actualizado`, single, bulk or from the edit form) requires the user to enter that date (`fechaActualizacion` aaaa-mm-dd, inside the current cycle and not in the future, `proveedoresCiclo.js#fechaActualizacionDe`), which becomes both `fechaActualizacion` and `aprobadoAt` and is audited; `esExcepcion` providers (settable on create/edit, needs a `motivoExcepcion`) never take part in the cycle. Excel migration/normalization/integrity scripts live in `backend/scripts/proveedores/` (see its README; config in `mapeoProveedores.json`).
- **Valoración IA de compras (`lib/valoracionIA.js`, `lib/valoraciones.js`, `lib/valoracionAuto.js`, `app/api/records/[id]/valoracion`, `app/api/proveedores/[nit]/compras`)**: cada compra radicada recibe una `ValoracionCompra` (una por registro, puntajes 1–5 de la compra y del proveedor + observaciones que explican por qué + factores). `valoracionIA.js` es el núcleo puro (solo imports relativos, recibe el cliente Prisma) que arma el contexto completo del registro, del proveedor y de sus compras ANTERIORES, aplica la rúbrica y guarda; lo usan la app y `scripts/valoraciones/valorarRegistrosRadicados.mjs`. Al radicar, el frontend abre `ValoracionModal` que genera y guarda la valoración (`POST`); se ve en la columna Valoración IA de Registros y, en el detalle del proveedor, en la pestaña Compras y calificaciones (historial + calificación general = promedio del puntaje de proveedor), que también alimenta la columna Calificación IA de la tabla de proveedores. `valoracionAuto.js` (arrancado desde `instrumentation.js`) valora en segundo plano, al arrancar el backend y cada 30 min, las radicadas sin valoración, así al publicar los registros existentes quedan valorados solos (idempotente; usa `ANTHROPIC_API_KEY` del servidor; `VALORACION_AUTO=0` lo desactiva). Reglas de la rúbrica a respetar: la fecha de registro solo se usa si no es de una carga histórica (>30 registros creados el mismo día) y las valoraciones previas de la IA nunca se realimentan como contexto.
- **Presupuesto (`lib/presupuestos.js`, `app/api/presupuestos/*`)**: per-year, per-area purchasing budgets (`PresupuestoAnio`, `Presupuesto`, `PresupuestoCategoria` models). A year's `modo` is either `"area"` (one total per area) or `"categoria"` (split across categories, summed for the area total); switching modes when budgets already exist requires `confirm: true` and deletes the existing ones (`POST /api/presupuestos/modo`). Everything (including reads) is gated by `viewPresupuesto` (default: admin only). Feeds the budget-risk alert below.
- **Solicitudes de compra (`lib/solicitudesCompra.js`, `app/api/solicitudes-compra/*`, `app/api/actividades/[id]/solicitudes`, `frontend/components/SolicitudesCompraView.jsx`, `bienestar/SolicitudesActividad.jsx`, model `SolicitudCompra`)**: whoever can edit an activity's línea requests a purchase from an already registered activity (ficha or edit form), only saying what they want and the date it must arrive. Whoever has `createRecord` sees it in Alertas y notificaciones › Solicitudes de compra (tab + count, plus a Mi día section) until it is handled: "Generar compra" opens `RecordModal` prefilled with the activity fixed (props `crear`, `actividadFija`) and the server associates the purchase to it itself; closing an activity cancels its unattended requests; "Rechazar" requires a reason, shown to the requester in the ficha. Pending requests add to the red count of the bell and the Alertas menu item of whoever has `createRecord` (`/api/notificaciones/bandeja/no-leidas` returns `solicitudes`; the bell links to that tab when only requests are pending) — they never go to the Bandeja. The outcome sends the requester a direct notice (`NotificacionEntrega` with `ejecucionId` null and `contenido.sistema`, not tied to a configured rule). Audited as `solicitudCompra`.
- **Agentes de Compras (page `/agentes` in the Compras menu, `lib/agentesCompras.js`, `app/api/agentes-compras/*`, `frontend/components/compras/agentes/*`, migration `cuadros_compras`)**: same rules as the Bienestar agents — they run only when a person asks, the code computes every figure and alert, Nova only writes (summaries, a category from the catalog, explanations) and **no agent changes a purchase**. (1) **Revisor** (`revisarCompra`, `POST /revisar`): checks a draft or saved purchase — cuadro comparativo threshold (2/4 SMMLV from Maestros; ok if a Compras cuadro is attached via `CuadroComparativo.recordId`), split purchase (same supplier AND same need, ±30 days, together over 2 SMMLV), supplier status (`listMaestroProveedores` → `alerta`), possible duplicate, invoice number reused by another supplier, price vs. the median of similar purchases; Nova checks category coherence. Also in `RecordModal` as the "Revisar la compra" button (results in `HallazgosRevision.jsx`, never blocks saving; not to be confused with the older "Revisar con Nova" of Observaciones). (2) **Proveedor y precio** (`proveedorYPrecio`): similar purchases by IDF-weighted word coverage, price range, suppliers with Nova valuation and cycle status. (3) **Cotizador**: `lib/agenteCotizador.js` with `modulo: "compras"` (`CuadroComparativo.modulo` separates the lists) and optional `recordId`; the `Cotizador.jsx` component takes `base` + `conCompra`. (4) Verificar factura was removed in November 2026 (the `verificacionFactura` audit label stays only so old entries still read well). (5) **Vigía de presupuesto** (`vigiaPresupuesto`, gated by viewPresupuesto): per area/category spent, monthly pace, year-end projection and month it runs out. (6) **Detector de anomalías** (`detectarAnomalias`, feature `viewAnomaliasCompras`, admin by default): split purchases, duplicates, prices ≥2× the median of similar earlier ones, a supplier with >40 % of an area. `POST /lectura` recomputes the figures server-side and Nova explains them (vigía/anomalías, on demand). Feature `viewAgentesCompras` (Compras tab of the Matriz, section Agentes; **admin only by default**, assignable to any role, custom ones included) gates the page, agents 1–3, their routes and the "Revisar la compra" button of the form (`RecordModal` prop `puedeRevisar`, passed by `RegistrosView`). Similarity uses IDF-weighted words (`indice`/`parecido`/`cobertura`), so common words like "servicio" or "capacitación" weigh little.
- **Mi correo y agente de correo (`lib/correoGraph.js`, `lib/correoCuentas.js`, `lib/cifradoTokens.js`, `lib/agenteCorreoProveedores.js`, `lib/solicitudesProveedorCorreo.js`, `app/api/correo/*`, page `/mi-correo`, `frontend/components/correo/*`, models `CuentaCorreo`/`CorreoRevisado`/`SolicitudProveedorCorreo`, migration `correo_agente_proveedores`, setup in `docs/correo-agente-proveedores.md`)**: each person with the Matriz feature `vincularCorreo` (General; default admin + proveedores) links their Microsoft 365 mailbox through Microsoft Graph OAuth (delegated, read-only `Mail.Read`; only the mailbox with the same email as the panel user; signed `state` + nonce cookie; tokens AES-256-GCM encrypted, never sent to the client or audit). `CORREO_MODO` desactivado/simulado/real (`MS_GRAPH_TENANT_ID`/`CLIENT_ID`/`CLIENT_SECRET`, `CORREO_CLAVE_CIFRADO`); in simulado, Mi correo has "Probar con un correo" (paste + optional RUT). With the person's switch on (`agenteActivo`), `startAgenteCorreo` (instrumentation, every 10 min, `CORREO_AGENTE_AUTO=0` disables) reads new Inbox mail; a code filter (`pareceSolicitud`) sends only provider-registration emails to Nova (max 20 per run, each message once via `CorreoRevisado`), which reads the email + the RUT attachment (NIT from box 5 without DV, checked by `prepararArchivo`) and picks catalog values that the code validates. The result is a `SolicitudProveedorCorreo` + a system notice in that person's Bandeja (`contenido.fuente: "correo"`, `solicitudCorreoId`), rendered by `SolicitudProveedorCorreo.jsx`: complete (NIT valid and new, nombre, descripción — `calcularFaltantes`, recomputed on read) → "Agregar proveedor"; otherwise `ProveedorFormModal` (props `inicial`/`guardar`/`aviso`) opens with the missing fields in red. Approving (`editProveedores`) goes through `createProveedor`; nothing is created without a person. Audited as `cuentaCorreo` and `solicitudProveedorCorreo`.
- **Salario mínimo (`lib/salarioMinimo.js`, `/api/maestros/salario-minimo`, model `SalarioMinimo`, section "Salario mínimo" in Maestros de Compras, `components/ConfigSalarioMinimo.jsx`)**: SMMLV per year (value + decree), managed by `viewMaestros`, audited as `salarioMinimo`. Migration `salario_minimo` seeds 2025 ($1.423.500, Decreto 1572 de 2024) and 2026 ($1.750.905, Decreto 1469 de 2025 ratified by Decreto 0159 de 2026). `salarioVigente()` returns the current year's (or the latest one with `exacto: false`); the cotizador uses it for the cuadro comparativo threshold. Add each new year when its decree comes out.
- **Nova: filtros por nombre y valor sin IVA (`agentTools.js#resolverFiltros`, rules 8c/8d of the chat)**: area/category/state filters no longer need the exact name — if none matches exactly, values containing every word are used and the tool returns `notaFiltros` (how it was read, or similar names when nothing matches) so Nova never answers "0 compras" because of a missing "(JPA)". `buildAggregates` also returns `comprasConValorSinIva` and `valorConIvaDeEsasCompras`, because many purchases lack the without-VAT value: Nova must say the without-VAT total covers only N of M purchases.
