# Roles personalizados y Matriz de permisos

Detalle movido desde `CLAUDE.md` (sin cambios de contenido). Las convenciones generales siguen en `CLAUDE.md`.

- **Roles personalizados (`lib/rolesCatalogo.js`, `lib/rolesPersonalizados.js`, `app/api/roles/*`, `frontend/components/RolesView.jsx`, tab Usuarios › Roles)**: besides the 5 system roles in `lib/roles.js` (they keep hard-coded rules: Legalizar's editable fields, radicado…), admins create roles in the UI (model `RolPersonalizado`, table `roles`; `User.role` stores its `clave`, a lower-case slug). A custom role has **no** default permissions: its features are `RolePermission` rows, i.e. the same Matriz (which now shows one column per role, system + custom). Editing a role's features goes through `setPermission` (audited as `permiso`); create/rename/delete are audited as `rol`. System roles can't be renamed or deleted; a custom role can't be deleted while users have it; Administrador can't be modified. Anything that validates or labels a role must use `rolesCatalogo.js` (`esRolValido`, `nombreDeRol`, `todosLosRoles`), never `ROLE_LIST` alone; `/api/auth/me` returns `roleLabel` for display. Seeded role **Bienestar** (migration `roles_personalizados`): viewBienestar, editBienestar, viewRegistros, viewAgenteIA, viewNotificaciones. Seeing Registros is now the Matriz feature `viewRegistros` (default: the Compras roles), so a custom role can be given it; roles without it are sent to /bienestar or /proveedores, and the landing page falls back to /bienestar.
- **Matriz de permisos (`lib/permissions.js`)**: a runtime permissions layer on top of `lib/roles.js`'s static defaults, gated by the dynamic feature `viewUsuarios` (not a hardcoded `role === "admin"` check) and surfaced in the frontend inside `UsuariosView.jsx` (`components/PermissionsMatrix.jsx`). `FEATURES` is a hardcoded catalog of toggleable features, each with a `modulo` (Compras, Bienestar, Tesorería or General, the tabs of the Matriz; a new feature must have one) and a `defaultRoles` list. Bienestar and Fundación have separate features (`viewDashboardBienestar`/`viewBienestar`/`editBienestar`, `viewDashboardFundacion`/`viewFundacion`/`editFundacion`, plus the shared `viewMaestrosBienestar`): routes of one activity use `apiGuard.js#requirePermisoActividad(id, "ver"|"editar")`, which picks the feature from the activity's línea. Each default list matching `lib/roles.js`'s current behavior. `isRoleAllowed(role, featureKey)` — called from almost every route handler instead of a static role check — looks up an exception row in `RolePermission`; if none exists (or the lookup fails), it falls back to `defaultRoles`, so a data/connection issue never silently revokes access. `admin` always returns `true`, regardless of any stored row. `setPermission()` upserts an override and audit-logs the change (`entityType: "permiso"`). `GET /POST /api/permissions` exposes `getFullMatrix()`/`setPermission()`; `getEffectivePermissions(role)` backs the `permissions` map returned by `GET /api/auth/me`.
