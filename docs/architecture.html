Panel de Compras y Bienestar — Full Architecture

Data Models (Prisma Schema)

Core entities in PostgreSQL, accessed via Prisma ORM:

  • Record — purchase order (fecha, proveedor, área, estado, valores, radicado, etc.)
  • User — dashboard user (email, role, bcrypt password, active flag)
  • Maestro — catalog item (area, responsable, estado, categoría, medioPago, etc. — dropdown options)
  • Presupuesto* — budget (per-year, per-area, per-category if applicable)
  • AuditLog — every change (user, entity, action, timestamp, before/after JSON)
  • Conversation / Message — AI chat history
  • ReportConfig — automated report schedules & templates

Backend Route Structure (/api)

Records & Core

  • GET /api/records — list (filters, pagination)
  • POST /api/records — create
  • PATCH /api/records/[id] — edit
  • DELETE /api/records/[id] — soft/hard delete
  • GET /api/maestros — dropdown options

Auth & Admin

  • POST /api/auth/login — issue session cookie
  • GET /api/auth/me — session user + permissions
  • POST /api/auth/logout — clear cookie
  • GET/POST /api/users — user CRUD (admin only)

Analytics & AI

  • GET /api/alerts — pending, overdue, budget risk
  • POST /api/agent/chat — stream AI responses
  • GET/POST /api/reports — report builder/scheduler

Permissions & Audit

  • GET /api/permissions — effective perms for user
  • POST /api/permissions — admin override (audited)
  • GET /api/audit — change log

Frontend Page Routes

  • /dashboard — KPI cards, charts (BarChart, StackedBar SVG components)
  • /registros — table, filters, CRUD modals, export (CSV/PDF/Word)
  • /usuarios — user management + Permissions Matrix editor
  • /maestros — catalog admin (dropdown options)
  • /presupuesto — budget per-year/per-area configuration
  • /alertas — pending, overdue, budget-risk alerts
  • /auditoria — change log viewer
  • /informes — report builder/scheduler/executor
  • /agente-ia — chat interface
  • /login — session start

AI Integration (Anthropic)

Backend only — Frontend never calls Anthropic directly. Three use cases:

1. Chat (Agente IA)

User sends message → lib/aiChatCascade.js streams to Claude (streaming endpoint). Context includes recent records, user role, alerts. Responses appear in browser in real-time.

2. Structured AI

lib/aiStructured.js uses non-streaming JSON mode for extraction/classification. Used by: report content generation, "explain this number", moderation checks.

3. Reports (Informes Automáticos)

lib/reportScheduler.js checks daily. Calls AI to generate report blocks (KPIs, summaries, insights). Runs in-process; built PDF + HTML email body; saved to disk.

Alerts Review

app/api/agent/review-alertas — AI analyzes current alerts (pending, overdue, budget). Reuses exact same alert data as the frontend sees (intentional — consistency).

Session & Auth Model

  • Session token — HMAC-signed (Web Crypto, works in Node + Edge middleware), httpOnly cookie
  • Same secret in both apps — SESSION_SECRET env var, so Frontend & Backend can independently verify cookies
  • Middleware — Backend middleware.js checks every /api/* route (except login), returns 401 if invalid or expired
  • Permissions — stored in RolePermission table (admin overrides), returned by GET /api/auth/me alongside user data
  • Fallback — if permissions lookup fails, uses static lib/roles.js defaults (safety first)

Database Deployment

  • Migrations — managed via Prisma: npx prisma migrate dev --name <name> (dev), npm run prisma:deploy (prod)
  • Seed — npm run db:seed runs prisma/seed.mjs, which loads seed-data.json (sample data only)
  • Real data — replace seed-data.json with actual export, re-run seed

Scaling Considerations

  • Current state — everything in one Backend instance (routes, AI, scheduler, report jobs)
  • If reports/AI slow down UI — move job queue (Bull, RabbitMQ) + separate worker service
  • If routes grow (50+) — consider NestJS (better structure, DI, validation)
  • If multi-region — cache session secret, use read replicas for queries
  • Current guardrail — lib/permissions.js and lib/records.js are DB-agnostic, so switching ORMs is low-friction
